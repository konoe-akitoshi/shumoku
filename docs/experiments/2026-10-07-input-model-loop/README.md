# 入力モデルの再設計ループ

方針は [`docs/network-model.ja.md`](../../network-model.ja.md)（PR #816）。
`model.ts` が今の最小モデル。`data/` は `examples/` を新形式に書き換えたもの。
`bun check.ts <例の名前...>` で、新形式→旧 YAML へ派生させ、元の YAML と
パース結果と SVG を比べる。

## 2周目（2026-10-08）: 場所のグループ・セグメント・事実のフィールド化

足したもの: `groups`（場所だけ、入れ子可）、`segments`（VLAN・共有セグメント、`vlan`/`prefix`）、
ノードの `vendor`/`model`/`address`/`description`/`group`、リンクの `speed`/`segments`、
端点の `address`。ラベルは名前だけにし、事実の行は派生側で組み立てる。

`data/` は手で書き直した（1周目は機械下書き）。

**再現できたもの**: vendor/model（aws の service/resource を除く）、links.vlan（セグメントから全件）、
端点の IP、場所のグループ（拠点・クラウド・DC・Campus）。

**まだ落ちるもの**:

| 落ちたもの | 例 | 判定 |
| --- | --- | --- |
| 状態 | Active / Planned / Staged / Inventory / Decommissioning、Failed / Offline | 前者はライフサイクル（構成）、後者は観測（後段）。2例 |
| 場所でないグループ | Edge / Security（役割）、Production / Staging（環境）、VMware Cluster | 意味ごとに別の答え。下記 |
| 集約ノード | 「RT1/RT2」「FW1/FW2」「2x ESXi + VMs」「2x 1G (RT1/RT2)」 | 実データの不確かさと同じ根。候補 |
| トンネル | IPsec VPN ×3（dashed で表現） | 物理リンクと別種の接続。候補 |
| HA の組 | `redundancy: ha` ×4、「HA Keepalive」 | 候補 |
| VM と収容ホスト | 「vSwitch」リンク、Cluster の箱 | ケーブルでなく「上で動く」関係。候補 |
| LAG・回線の種類 | 「LACP 40G」「Dark Fiber」「PPPoE」、色で表した媒体 | 保留 |
| ソフトウェア・資源 | 「VMware ESXi 8.0」「4vCPU / 16GB」 | 保留 |
| 表示 | rank 50、style 47、settings 5、太字 | 対象外 |

**モデルが直したもの**: 共有セグメントのリンクで、両端の `ip` にネットワークアドレス
（`10.0.1.0/29`）が書かれていた。アドレスでなくプレフィックスなのでセグメント側に移した。

**派生側の課題**:

- 型番の表示名（`qfx5120-48y` → 「QFX5120」）はカタログが要る。
- prefix-subgraph のサブネットの箱は、ノードの address とセグメントの prefix から導ける。
  入力に書かなくてよい。
- 「10.1.20.1 (VLAN200)」の VLAN もリンクのセグメントから導ける。

**データの矛盾**: enterprise-ogp の web-srv（10.100.10.10）は、DMZ のゲートウェイ
（10.100.0.254/24）のサブネットの外にある。vm-app-01 と vm-db-01 は同じ /24 で VLAN が違う。

## 3周目（2026-10-08）: 実データ（人が手で書いた実トポロジー、60ノード/57リンク）

実データは公開できないので、変換したファイルはリポジトリに入れていない。
`bun check.ts <元.yaml>=<変換.yaml>` で手元のファイルを比べられる。ID を付け直したため、
比較はノードを ID、リンクを両端の組で突き合わせて行った。

足したもの: ノードとリンクの `assumed`（あると思うが確認できていない）、ノードの `members`
（1ノードが複数台を表す）、リンクの `description`。

**再現できたもの**: 60ノード・57リンクの構造すべて、場所の入れ子（会場→フロア）、型番、管理アドレス。

**モデルの方が正確になったもの**:

- ポートが分からない接続に、作者は `uplink:<IP>` のような**架空のポート名**を21個作っていた。
  ポートを省けるので要らなくなった。
- ルーターとファイアウォールの間の「VLAN10」リンクは、実際にはケーブルでなく、コアの中を通る
  L3 の隣接だった。ルーター→コア（ポート不明、`assumed`、セグメント VLAN10）と書き直せた。
- 確かさ（observed / unresolved / inferred / uplinkAssumed）とラベル内の「(unresolved)」は、
  `assumed` 1つに収まった。残りの区別（どう知ったか）は取り込み元の層の話。
- 名前の分からない AP 4台は、ラベルにベンダー名が入っていた。ラベルを空にできる。

**まだ落ちるもの**:

| 落ちたもの | 判定 |
| --- | --- |
| ~~トランクのサブインターフェースのアドレス（x5.10 に1つ、x5.100 に1つ）~~ | 解決: 下記 |
| 集約ノードのメンバーの名前とアドレスの対応 | 名前2つとアドレス2つは分かるが、どれがどれか不明 |
| HA の組（運用側の表では HA、実機では単体） | 例の `redundancy: ha` と同じ概念。主張と観測が食い違う |
| 「(旧)」 | 状態。例の Planned / Decommissioning と同じ |
| ファームウェアの版 | 例の「ESXi 8.0」と同じ |
| identity（MAC・sysName・外部 ID）、provenance、presence | 取り込み元の層。sysName と管理 IP はラベル・address と重複 |

**アドレスをセグメントへ移した**: 端点の `address` をやめ、`segments[].addresses`（ノード→アドレス）にした。
トランクは VLAN ごとに1つずつ持て、SVI のようにポートに付かないアドレスも書ける（nwdiag と同じ形）。
アドレスを持つノードは、そのセグメントを運ぶリンクの端点でなければならない。例の端点 IP は全件再現。
変換した実データは archive の `events/seccamp-2026/derived/input-model-loop/` に置いた。

残る問い: ノードの `address`（管理アドレス）も、管理セグメントのアドレスとして書けば要らなくなるか。

## ブラインドテスト（2026-10-08）: 型定義だけを Haiku に渡す

`model.ts` の型定義（パーサーより上）だけを渡し、既存コードと設計文書は見せなかった。

- 書く ×3: `blind/task-write.md` の文章から YAML を書かせた。正解は先に書いた `blind/key.yaml`。
  出力は `blind/haiku-*.yaml`。
- 読む ×2: enterprise-ogp（コメント除去）を渡し、8問に答えさせた。

**できていたこと**: 書いた3つはすべて検証を通った。場所の入れ子以外の構造（トランク、
セグメントのアドレス、`members`、未確認のノードとリンク、不明ポートの省略）は3体とも正解と一致。
読む2体は8問すべて正答し、「書かれていないことは書かれていない」（fw-ha の場所）と答えた。
web-srv のアドレスがサブネットの外にある矛盾にも2体とも気付いた。

**全員がつまずいたこと**:

| つまずき | 件数 | 原因 |
| --- | --- | --- |
| 管理アドレスをノードに書くかセグメントに書くか | 5/5 | ノードの `address` とセグメントの `addresses` が同じ事実の置き場所として重なっている。書き手はセグメントだけ ×2、両方 ×1 に割れた（正解も両方に書いていた） |
| 未確認リンクに、書かれていない VLAN を足した | 3/3 | 書き手は検証コードを見ていない（型だけ）。3体とも「sw-2a のリンクからの類推」と書いている。リンクに `segments` が無いことが「不明」とも「運ばない」とも読めるのが原因の候補。別途、検証の「アドレスを持つノードはそのセグメントを運ぶリンクが必要」という制約は、足さずに正直に書いた版を拒む（確認済み）ので、これも外すべきだった |
| vendor / model / type の表記がばらばら | 3/3 | 語彙が無い（`Fortinet`、`switch`、`onu`）。カタログの層 |

**根拠の強さ**: 5体は同じモデルの5回の試行で、独立した5つの証拠ではない。読み手への問4
（web-srv と fw-ha のアドレスは種類としてどう違うか）は混乱を誘う聞き方だった。

**読み手が指摘したこと**: edge-rt-ha と fw-ha はラベルが HA なのに `members` が無い
（変換時の見落とし）。仮想リンク（vSwitch）と物理ケーブルが区別できない（VM と収容ホストの候補と同じ）。

## 4周目（2026-10-08）: アドレスをセグメントに一本化

ブラインドテストを受けて:

- ノードの `address` をやめ、アドレスはすべて `segments[].addresses` に書く。1ノードが同じセグメントに
  複数のアドレスを持てる（1つなら素の文字列、複数ならリスト）。
- 「アドレスを持つノードはそのセグメントを運ぶリンクの端点」という制約を外した。リンクが分からなくても
  セグメントに属せる（nwdiag と同じ）。
- `members` を名前のリストにした。メンバーのアドレスは集約ノードのアドレスとしてセグメントに書く。
  実データの「名前2つとアドレス2つの対応が不明」が、そのまま書けるようになった。
- enterprise-ogp の HA ノード2つに `members` を付けた（読み手の指摘）。

例で、どのネットワークか書かれていない名前の下の IP は、属性の無い `mgmt` セグメントに入れた。
**これは誤り**: netbox-enhanced では東京・大阪・本社の機器が1つの L2 ネットワークにいると主張したことになる。
「IP は分かるがネットワークは分からない」は、ノードの `address` でしか正直に書けない。
削除は欄を消す以外の案と比べずに決めており、再テストもしていなかった。次のテストで比べ直す。
prefix-subgraph はアドレスが各セグメントの prefix にちょうど収まり、サブネットの箱をセグメントから導ける。

**失ったもの: どのアドレスが管理用か。** ラベルに出す IP を選べず、全アドレスを並べることになった
（例の差分が増えたのはこのため）。機材ごとに当てはめると:

| 機材の管理のされ方 | 書けるか |
| --- | --- |
| L2 スイッチの管理 VLAN 上の SVI（実データのスイッチ群） | 書ける（管理 VLAN のセグメント） |
| 専用の管理ポート（fxp0 / Mgmt0 など、アウトオブバンド） | 書ける（管理網のセグメント。リンクは不明でよい） |
| クラウドやコントローラー経由でしか見えない AP | 書ける（その経路のセグメント、または無し） |
| 同じセグメントに管理 IP とインターフェース IP（実データのファイアウォール .101 / .254） | 両方書けるが、どちらが管理用か言えない |
| HA の仮想 IP と各機の IP | 全部書けるが、どれが仮想 IP か言えない |
| ルーターのループバック（どの L2 セグメントにも属さない /32） | データにまだ無い。来たら1ノードだけのセグメントになり不自然 |

「管理用」は、取り込み元との突き合わせ（`identity.mgmtIp`）、監視の対象、表示に使う。前の2つは後段の層。

## 5周目（2026-10-08）: 2案を同じ条件でブラインドテスト

4周目の削除を見直すため、案A（アドレスはセグメントだけ）と案B（ノードに「セグメントが分からない
アドレス」として `address` を残す）を比べた。型は `blind/types-a.ts` と `blind/types-b.ts`、
タスクは `blind/task-write-2.md`、正解は結果を見る前に書いた `blind/key-2a.yaml` と `blind/key-2b.yaml`。
各案に Haiku ×2、Sonnet ×1。出力は `blind/r2-*.yaml`。

| 問い | 案A | 案B |
| --- | --- | --- |
| 「ネットワーク不明の NAS 10.0.0.5」を正直に書けたか | 0/3（空のセグメントを作った ×2、説明文に埋めた ×1） | 3/3（`address`） |
| 「VLAN 未確認のリンク」に VLAN を足さなかったか | 3/3 | 3/3 |
| 書かれていない VLAN をほかのリンクに足したか | 1/3（プリンターのリンク） | 0/3 |

案B では「到達できるアドレス」も全員がプレフィックスからセグメントに書き、`address` を使ったのは
本当にネットワークが分からない NAS だけだった。前回の混乱は欄があることではなく、
「Management address」という意味づけが原因だったと考える。**案B を採用した。**

- `address` は「セグメントが分からないアドレス」。同じアドレスをセグメントにも書くと検証で落ちる。
- 4周目に作った属性の無い `mgmt` セグメント（例3本）と、実データの `ap-mgmt` / `controller-mgmt` を外し、
  ノードの `address` に戻した。prefix-subgraph の `mgmt` は元データにサブネットがあるので残した。

**残った問い**: リンクに `segments` が無いことが「不明」とも「運ばない」とも読める（6体中4体が指摘）。
今回はタスク文に「書かれていない事実を足さない」と入れたので全員が省いたが、1回目のテストでは
3体とも類推で足した。この一文の有無が条件として違うので、1回目と2回目の結果は直接比べられない。

## 気付いたこと

- ポートを省くと、旧パーサーは毎回違う ID のポートを作る（比較では出現順に置換）。
- `bandwidth: 1G` は例の中で多用されているが、パーサーは読まずに捨てている。
- `location-based.yaml` は今のパーサーが扱わない形式（`network.locations`）。
- 例の作者は「shared segment」をリンクの label で、VLAN セグメントを subgraph で表している。
  セグメントという概念が無いことの回避策に見える（他ツール集計とも一致）。
