# 入力モデルの再設計ループ

方針は [`docs/network-model.ja.md`](../../network-model.ja.md)（PR #816）。
`model.ts` が今の最小モデル。`data/` は `examples/` を新形式に書き換えたもの。
`bun check.ts <例の名前...>` で、新形式→旧 YAML へ派生させ、元の YAML と
パース結果と SVG を比べる。

## 変更の手順

判定の基準は1つ: **分かっていることを、過不足なく書けるか。** 足すことを強いる形（捏造）も、
捨てることを強いる形（欠落）も不合格。4周目はこの基準に反した変更を2つ入れた。

1. 失敗の仕組みを確かめる（話を作らない。書き手に見えていない検証は書き手の振る舞いの原因にならない）。
2. 直し方を2つ以上出す。
3. 各案で `bun fixtures.ts` を通す。`fixtures/pass` はループで出会った知識の状態で、書けなくなったら
   その案は捨てる。`fixtures/fail` は拒むと決めた形。新しい失敗を見つけたら fixture を1つ足す。
4. 迷う案はブラインドテストで比べる。正解を先に書く、誘導的な質問をしない、複数のモデル、
   案どうしの条件をそろえる。
5. `bun check.ts` で例と実データを通す。

**止めるとき**（2026-10-08、自動で回すにあたって決めた）:

- 収束: 候補を1つ片付けても新しい候補が出ず、残りがすべて入力モデルの外（後段の層）と判断できる。
  ブラインドテストで2体以上が同じ点に迷っていない。
- 問題: 人が決めるべき価値の問い（入力モデルの範囲など）、判定基準どうしの衝突、同じ失敗の再発。
- push・PR・実データの公開はしない（PR はユーザー判断で 2026-10-08 に作った）。

fixture を過去の版にかけると、3周目の版はポートの無いアドレスを、4周目の版はネットワーク不明の
アドレスを拒む。どちらもこの手順なら変更前に止まっていた。

`model.als` は構造だけを Alloy で書いたもの。`run` は知識の状態が書けるか、`check` は望まない形が
書けてしまうかを、小さい範囲の全組み合わせで調べる。実行は Alloy 6.2.0 の jar で
`java -jar org.alloytools.alloy.dist.jar exec -f -t text model.als`。

2026-10-08 の結果: `run` 4件はすべて SAT（書ける）。`check` 3件はすべて反例あり。自己ループのリンク、
同じセグメントで別ノードが同じアドレス、全体で別ノードが同じアドレス（HA の仮想 IP なら正当かもしれない）。
どれもパーサーが黙って通す、まだ決めていない形。

3周目のリンク必須の制約を足すと「ポートの無いアドレス」が UNSAT になり、Alloy はこの失敗を捕まえる。
4周目の失敗（欄の削除）は捕まえられない。欄が無いと「ネットワーク不明のアドレスがノードにある」という
状態自体を Alloy で書けないため。**Alloy は制約のかけ過ぎに効き、語彙の不足には効かない。**
語彙の不足は fixture とブラインドテストの役目。

## 4周目（2026-10-08）: アドレスをセグメントに一本化

ブラインドテストを受けて:

- ノードの `address` をやめ、アドレスはすべて `segments[].addresses` に書く。1ノードが同じセグメントに
  複数のアドレスを持てる（1つなら素の文字列、複数ならリスト）。
- 「アドレスを持つノードはそのセグメントを運ぶリンクの端点」という制約を外した。リンクが分からなくても
  セグメントに属せる（nwdiag と同じ）。
- `members` を名前のリストにした。メンバーのアドレスは集約ノードのアドレスとしてセグメントに書く。
  実データの「名前2つとアドレス2つの対応が不明」が、そのまま書けるようになった。
- enterprise-ogp の HA ノード2つに `members` を付けた（読み手の指摘）。

例で、どのネットワークか書かれていない名前の下の IP は、属性の無い `mgmt` セグメントに入れた。
**これは誤り**: netbox-enhanced では東京・大阪・本社の機器が1つの L2 ネットワークにいると主張したことになる。
「IP は分かるがネットワークは分からない」は、ノードの `address` でしか正直に書けない。
削除は欄を消す以外の案と比べずに決めており、再テストもしていなかった。次のテストで比べ直す。
prefix-subgraph はアドレスが各セグメントの prefix にちょうど収まり、サブネットの箱をセグメントから導ける。

**失ったもの: どのアドレスが管理用か。** ラベルに出す IP を選べず、全アドレスを並べることになった
（例の差分が増えたのはこのため）。機材ごとに当てはめると:

| 機材の管理のされ方 | 書けるか |
| --- | --- |
| L2 スイッチの管理 VLAN 上の SVI（実データのスイッチ群） | 書ける（管理 VLAN のセグメント） |
| 専用の管理ポート（fxp0 / Mgmt0 など、アウトオブバンド） | 書ける（管理網のセグメント。リンクは不明でよい） |
| クラウドやコントローラー経由でしか見えない AP | 書ける（その経路のセグメント、または無し） |
| 同じセグメントに管理 IP とインターフェース IP（実データのファイアウォール .101 / .254） | 両方書けるが、どちらが管理用か言えない |
| HA の仮想 IP と各機の IP | 全部書けるが、どれが仮想 IP か言えない |
| ルーターのループバック（どの L2 セグメントにも属さない /32） | データにまだ無い。来たら1ノードだけのセグメントになり不自然 |

「管理用」は、取り込み元との突き合わせ（`identity.mgmtIp`）、監視の対象、表示に使う。前の2つは後段の層。

## 6周目（2026-10-08）: HA の組

**仕組み**: HA は4通りに現れた。別ノードの組でリンクに `redundancy: ha`（例 ×4。旧レイアウトは
これで2台を並べる）、1ノードにまとめた組（Edge Routers (VRRP)）、運用の表では HA だが未確認の組
（実データ）、組を結ぶリンクが分からない VRRP（よくある構成）。

**案**: A リンクに印（旧形式）は、組を結ぶリンクが無いと印を付ける先が無く、ケーブルを作ることになる。
D ノードに `peers` は、同じ事実を両側に書く。どちらも fixture の段階で落とした。
B1（トップレベルの組がノードを列挙）と B2（ノードが組を指す、`group` と同じ形）をブラインドテストで比べた。
型は `blind/types-ha-*.ts`、タスクは `blind/task-ha.md`、正解は `blind/key-ha-*.yaml`、出力は `blind/ha-*.yaml`。

| 書けたか | B1 | B2 |
| --- | --- | --- |
| VRRP の組と仮想アドレス（組の id の下）、未確認の組に `assumed` | 3/3 | 3/3 |
| スタックを `members`、つながり不明の fw-b にリンクを作らない | 3/3 | 3/3 |
| 誤り | 1/3（組でなく fw-b 自体を `assumed` にした） | 0/3 |

差は出なかった。**B1 を採用**: B2 は「ノードは組を1つしか持てない」という、データに根拠の無い制約を
作り込む（3周目と同じ種類の誤り）。テスト前に、`members` のコメント（「HA ペアやスタック」）が
新しい組と重なっていたのを「スタックのユニット」に直した。

- `redundancy: [{ id, label?, nodes, assumed? }]`。仮想アドレスはセグメントに組の id で書く。
  組とノードの id は同じ名前空間。2台未満の組と自己ループのリンクは拒む（後者は Alloy の指摘）。
- 組を結ぶリンクの印は導ける（両端が同じ組）。例の `redundancy: ha` 4件はすべて再現した。
- 実データの「運用の表では HA、実機は単体」を、`.102` を正体不明のノードとして置き、組に `assumed` で書いた。
  元の作者は「確認済みノードとしては描かない」としていた。応答した事実だけを書いている。

Alloy: 組を足しても書けるべき状態はすべて SAT。仮想アドレスがメンバー自身のアドレスと同じ形が
書けると分かったが、VRRP のアドレスオーナー（仮想アドレス＝実アドレス）は正当なので許す。

**6体中5体が迷ったこと**: つながりの分からない機器（fw-b）で、「接続不明」と「つながっていない」が
同じ形になる。リンクに `segments` が無いときの「不明 / 運ばない」と同じ根。次の候補。

## 7周目（2026-10-08）: 「分からない」と「無い」

**仕組み**: 欄を書かないことの意味が、ポート（型に「分からない」と書いてある）以外では決まっていなかった。
5周目と6周目のテストで計9体が「不明と無しが区別できない」と指摘した（リンクの `segments`、つながり不明の機器）。

**案**: 0 今のまま、A「書いていないことは分からない」を文書全体の約束として1文書く、C A に加えて

## 9周目（2026-10-08）: VM と稼働基盤

**仕組み**: 旧実装は VM と収容ホストの関係を持っていなかった。8周目の V1（VM を仮想スイッチへのリンクで書く）は、

## 全体の見直し（2026-10-08、PR の前）

**実データ**: 3周目の実トポロジー由来の値（私設アドレス、機器名、作り手名）が fixture と本文に残っていた。

**モデル**（sol のレビュー10件と自分の読み）。直したもの:

- 冒頭の規則が「書いていないことは分からない」だけで、書いたノードやリンクが存在すると言えるのかが
  書かれていなかった（読み手 luna が `assumed` の無いノードを「存在は分からない」と読んだ 0/5 の一因）。
  「書いたものは分かっていること、`assumed` が無ければ存在は確か」を足した。
- `segments: []` が「書いていない」に化けていた。空のリストは「何も運ばない」として残す。
- `host` の循環検出が Alloy（組は全メンバーを指す）とずれていた。組どうしの循環を見逃し、組の中の1台が
  輪になるだけで弾いていた。Alloy と同じ「どれを選んでも戻ってこない」に揃えた。
- 組の `nodes` とノードの `members` に同じ名前を2度書けた。拒む。
- セグメントへのリンクに `segments` を書けた（どちらが正しいか読めない）。2台を結ぶリンクだけが運ぶ。
- `RoutingDomain.prefix` が1つだけだった（VPC は IPv4 と IPv6、追加の範囲を持つ）。セグメントと同じくリストも可。
- `addresses` のコメント「ノードの持つ全アドレス」が冒頭の「部分的でよい」と矛盾。直した。
- 値を空にした欄（`asn:  # not specified`）と、宣言していないグループへのエラーを、直し方の分かる文にした。

見送ったもの: セグメントの場所とノードの場所の食い違い（場所の入れ子を含めた意味を決めていない）、
AS 名の検査が AS65000 という名前の VRF も弾くこと（名前で判定する割り切り）、IPv6 の表記ゆれ、
アドレスやプレフィックスの書式の検査。

**人による確認キット**の `types.ts` が 13周目のままだった。今のモデルから作り直し、luna の基準を取り直した:
