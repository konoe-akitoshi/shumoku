# Shumoku ネットワークモデルの概念選定レビュー

**既存の図・Editor・Server・参照規格から独立して要求を置き直し、初期コアの範囲と用途別の方式を選ぶ。**

更新日: 2026-10-06。状態: M0 の比較検討と修正提案。P1a の表示分離を一部検証。概念選定全体の成立検証は未完了。
対象は [方針](network-model-direction.ja.md)、[論理設計](network-model-design.ja.md)、
[実装計画](network-model-implementation-plan.ja.md)。以下の判断は Shumoku への提案である。

## 結論と今回の修正

用途から完全に自由なモデルを作ることを目標にはしない。Shumoku が必要とする構造を、
特定の入力元・描画方式・更新処理の都合から分離して定義する。
旧案は変更時の整合性を詳しくした一方で、概念の選択理由と表現できない範囲が弱かった。

| 判断 | 修正後の位置付け |
| --- | --- |
| Node / Port / Connection | 初期コアの候補として維持。Node は文書内の要素、Port は物理・論理を含むその接続端点。実機そのものとの同一性は別の判断 |
| 二端点・無向の Connection | 初期に扱う接続関係の限定。共有媒体・有向関係・経路・包含を代表する汎用関係とはしない |
| Group | 任意の名前付き Node 集合までに縮小。親 Group、物理的包含、通信区画の振る舞いを初期コアから外す |
| 接続の physical / virtual / logical 分類 | コアの排他的な kind から外す。媒体・層・実現方法は別の意味として辞書や profile で定義する |
| 拡張・編集・収集 | 保持・参照検査・出所という要求と、envelope・Undo・sequence という方式を分ける。方式は P1 の比較対象 |

標準的な構造を目指すことは、今から全用途に共通する万能の形を確定することではない。
外部実装が同じ意味で読める範囲と、追加の契約が必要な範囲を公開することを最初の目標にする。

## 先に置く五つの要求

要素名や現在の package 構成から要求を導かず、consumer が必要とする判断で整理する。

1. **対象を追える**: 名前や表示を変えても、文書内の同じ要素と参照を追える。実機の同定は別に説明できる。
2. **関係の意味が読める**: 接続、包含、所属、依存、到達可能性を混同せず、分からないことを分からないまま保持できる。
3. **独立に解釈できる**: producer 名、Editor、collector、描画エンジンを知らなくても、対応する構造を読める。
4. **変更の影響が分かる**: 構造や拡張の参照を検査でき、未対応の情報を黙って失わない。保存と編集の方式は選べる。
5. **境界を越える追加を説明できる**: 用途別の属性追加、新しい関係、コア変更を区別し、未対応の意味を正しく診断できる。

Editor の Undo、containerlab の往復、Server の再収集は、この要求を検査する用途である。
それぞれの成功だけでは、他の用途でも意味が通ることの証明にはならない。

## 主要判断の比較

### 表示情報を外すだけの最小案

2026-10-05 の議論について提供された整理では、中心課題は構成と描画の混在であり、
既存モデルから座標やスタイルを順に分離する案が示されている。
相手側の発言が十分に記録されていないため、以下は仕様の合意ではなく、設計案との照合である。

| 項目 | 検討 |
| --- | --- |
| 要求 | 構成を正本として保存し、配置・スタイル・表示範囲を変えても接続と構成上の属性を変えない |
| 候補 A | 現在の概念を起点に、位置・見た目・配置制約・選択を分離する。構成用の新しい型は作るが、Port の別 collection 化などは同時に要求しない |
| 候補 B | 分離と同時に Node / Port / Connection / Group の再編、属性辞書、拡張契約を導入する。既知の問題をまとめて扱えるが、分離単独の効果を判断しにくい |
| 候補 C | containerlab などの既存形式を構成の正本にする。手書きの形は小さくなる可能性があるが、対応しない物理・論理情報と実行設定の扱いが別に必要 |
| 今回の判断 | P1a で A と B の小さな構成例を同じ選択・表示処理へ渡して比べる。まず表示分離の成立を確認し、B をそのまま採用済みとは扱わない。C は入出力評価の候補とする |
| 採否の条件 | A が複数 View・安定参照・不明端点・物理情報の保持を満たすなら、初期に B の追加概念を全部入れる必要はない。B の採用には、A で失われる意味や参照上の問題を例で示す |

互換性を制約にしないことは、既存の概念をすべて変更する理由にはならない。
新形式の必要性を示す比較には、今の概念を整理する小さい案も含める。
P1a での旧 renderer 向け派生表現は試作に使えるが、構成の正本へ書き戻さない。

### 議論と現行案の差分

| 議論された方針・提案 | 現行案との関係 | 今回の扱い |
| --- | --- | --- |
| 構成と表示の分離、構成を正本として保持 | 方針は一致していたが、原子的編集や source 更新が先に詳しくなっていた | 最初の試作を構成・表示分離と比較にする。拡張・更新の評価はその結果を受ける |
| 表示範囲の選択、折りたたみ、関心によるグループ化 | View に非表示や囲みはあったが、選択・集約の入出力が不足していた | View の論理的な selection と presentation、読み取り用の表示グラフを区別する |
| グラフとグループ階層は別 | 親 Group を初期 core から外した判断は、階層そのものの禁止ではない | 意味の定義された分類階層と、View の表示階層を別に検討する。接続構造へ木の制約をかけない |
| YAML を継続できる可能性と段階的な分離 | JSON 例と新 package 案が、新しい保存形式の決定に見えやすかった | 意味のモデル、アプリの型、保存形式を分ける。YAML を候補に残し、独自の新しい言語を初期条件にしない |
| 物理情報を別に重ねる、CSS で見た目を指定する | 物理 profile と View の分離は一致。スタイル方式の比較が不足 | 校正・長さ・設置場所は事実として保持する。CSS は SVG consumer の候補で、Canvas やデータモデルの必須契約にしない |

議論中に保留された境界・経路アルゴリズム・Link ID・形式利用の権利は、合意事項として補完しない。
構成側の接続 ID を持つ案は、平行接続や profile の参照を区別するためのこちらの提案である。
SVG に接続先 Node の ID だけを付けても、同じ二つの Node を結ぶ別の接続は区別できない。

### Node と Port の意味

| 項目 | 検討 |
| --- | --- |
| 要求 | 接続の対象と、その対象内の端点を別々に参照する。物理装置と論理要素を両方記述できる |
| 候補 A | Node を実機、Port を物理コネクターに限定する。物理配線には明快だが、論理 interface を別の概念で追加する必要がある |
| 候補 B | Node を文書内のネットワーク要素、Port をその要素が公開する端点とする。実機・connector・interface の詳細は意味の規約で区別する |
| 候補 C | すべてを一般的な Entity / Relation にする。表現自由度は高いが、基本描画や所有参照まで用途別規約なしには読めなくなる |
| 初期判断 | 再編案では B を試す。Port は一つの Node が所有する。Node / Port の ID は文書の参照 ID であり、ハードウェアの ID ではない。再編案全体の採用は P1a の最小分離案との比較で判断する |
| 制限と追加時の影響 | 部材 instance、connector の占有、interface の重ね合わせは別契約が必要。複数 Node が同じ実機を表す場合も自動統合しない。所有単位の変更は明示的な構造変更 |

ここでの「Node」は描画アイコンの種類で決まらず、「Port」はケーブルを挿す穴だけを意味しない。
ただし名前だけを一般化して、具体的な違いをすべて attributes に隠すことも避ける。
物理 connector と論理 interface の対応には型付きの関係が必要で、その仕様は初期コアの成立とは別に評価する。

### Connection の端点数と方向

| 項目 | 検討 |
| --- | --- |
| 要求 | 二つの既知の対象の接続を記述し、端点未特定も示す。共有媒体や依存関係を同じ事実と誤認させない |
| 候補 A | 無向・二端点の接続に限定する。基本配線・隣接関係の表現が小さく、制約を共有できる |
| 候補 B | 任意個数の端点と方向を一つの Connection に持たせる。多端点を表せるが、参加・送受信・共有媒体の意味を追加で決めないと解釈できない |
| 候補 C | 接続・参加・包含・依存などの型付き関係を最初から揃える。用途を説明しやすいが、初期規約が広がる |
| 初期判断 | A を採る。二端点という限定を公開し、B/C を代替候補として残す。層・媒体・実現方法が不明な Connection から通信可能性を推測しない |
| 制限と追加時の影響 | 共有媒体は単純な二端点の集合に展開しない。有向関係も表示矢印で補完しない。既存端点を参照する profile 内の関係は追加候補だが、共有媒体自体を共通 consumer が参照する要件ならコアの追加を再検討する |

二端点の選択は containerlab が採用しているからではなく、最初に同じ意味で検証できる範囲として選ぶ。
「physical / virtual / logical」は媒体・実現方法・抽象度が混ざるため、排他的な core enum を置かない。
`connection.technology` のような規約で確認できる技術を記録できても、そこから層や配線長は導かない。

端ごとの情報の参照にも選択がある。配列の slot を維持する案と、端点自体に ID を与える案を比べる。
現行図は slot 案を使う。P1 で端点の入替・付替えを試し、参照が安定しないなら公開前に修正する。
「無向の接続」という意味と、「配列の順序を保存する」という方式を同一の原則にはしない。

### Group と包含と区画

| 項目 | 検討 |
| --- | --- |
| 要求 | 同じ Node を複数の観点で選び、集合を表示以外からも参照できる。分類を通信や物理的な包含の証拠にしない |
| 候補 A | 分類・親子・包含・区画をすべて Group で表す。形は簡単だが関係の意味が不明になる |
| 候補 B | 任意の名前付き Node 集合のみを Group とする。集約の意味、親子、区画の規則は用途別にする |
| 候補 C | Group をコアから除き、集合をすべて View / profile に置く。コアは小さいが、表示以外から同じ集合を参照する共通契約が別途必要になる |
| 初期判断 | B を P1 の候補として選ぶ。Group が空または省略されても Node / Port / Connection を消費できる。初期の parentGroupId は削除する |
| 制限と追加時の影響 | Group の名前が Trusted zone でも通信制御や隔離を主張しない。VLAN の Port 所属、VRF、モジュール包含を nodeIds に押し込まない。P1 で表示以外の集合参照の必要性を示せなければ C を再検討する |

サイト・セキュリティ区画・装置内モジュールの階層は同じ関係ではない。
構造上の包含を扱う profile と、View の囲みを整理する階層はそれぞれの責務で定義する。
Group 階層を削除しても、Port の Node 所有関係は残る。

### 出所と更新処理

| 項目 | 検討 |
| --- | --- |
| 要求 | 設計と観測、出所、採取時刻、不在と未収集を区別し、再収集で設計を上書きしない |
| 候補 A | NetworkTopology 自体に収集状態・競合の勝者・更新順を入れる。単独の静的利用にも Server の状態管理が必要になる |
| 候補 B | 静的構造は単独で使え、主張・照合・更新の契約を追加で使う。処理方式を用途別に選べる |
| 候補 C | 出所を全部 adapter の内部に閉じる。構造は単純だが、設計と観測の差を第三者が説明できない |
| 初期判断 | B を選ぶ。出所や用途の意味を共通にし、SourceState / IdentityMap / Resolution は複数入力を扱う機能の責務とする |
| 制限と追加時の影響 | sequence の採番・record 全体置換・canonical ID の保管は収集試作の候補方式。単一ファイルの producer/consumer にこの方式や稼働中の resolver を要求しない |

観測 input が常に完全な topology を作れるという仮定にも偏りがある。
単一 Port の観測、所有 Node が未収集の入力は、観測契約で保持・診断する必要がある。
現行図の「各入力 topology は有効」は有効な topology を提供する adapter の対応範囲に限る。
不完全な主張までこの型へ変換できるとは主張しない。初期試作では未対応入力として理由を残し、
その情報を topology に出せないことと、観測自体が誤りであることを区別する。

### 拡張の参照と編集方式

| 項目 | 検討 |
| --- | --- |
| 要求 | 用途別情報を保持し、意味を知らない consumer でも対応能力を判断できる。編集が参照を壊す影響を調べられる |
| 候補 A | 全参照の envelope と payload 内の local key。未知 payload の対象を調べやすいが、参照一覧の完全性は profile 作成者の契約に依存する |
| 候補 B | payload に直接型付き参照を置き、共通の宣言的参照パスで列挙する。記述の間接性は減るが、条件分岐や未知の schema で完全な列挙が難しくなる |
| 候補 C | profile handler だけが参照を解釈する。用途の自由度は高いが、未導入 handler の影響を core 側で判断できない |
| 初期判断 | A を P1 の比較用実装にする。B の小さな対照例も作り、参照の列挙・変更・保存の負担を比較して公開前に選ぶ |
| 制限と追加時の影響 | 未知 payload に隠された ID の不存在は汎用 validator では証明できない。producer が参照契約を守る前提が必要。未知 profile が参照する削除を止めるのは初期 Editor の安全な方針であり、全 consumer の必須動作ではない |

未知 profile を明示的に外してから編集する、履歴として参照切れを許容する、読み取りだけ行う、
という consumer も考えられる。それぞれに保存文書の状態と能力を宣言する必要がある。
初期 Editor は有効な設計 project の保存を要求するため、削除・付替えを止める案を試す。
atomic な変更結果は要求するが、Undo に文書全体を保存するか差分を保存するかは Editor の実装方式である。

## 二端点以外の例を当てた結果

以下は紙上の反例によるレビューであり、実ネットワークの計測結果や対応実装ではない。
初期に全ケースを実装する要求ではなく、何が表せず、追加で何が必要になるかを確認する。

| ケース | 現行案への反例 | 修正後の境界と追加時の影響 |
| --- | --- | --- |
| 三つの端点が参加する共有セグメント | 三本の pairwise connection へ展開すると、元データにない直接接続や関係数を作る | 初期コア単独では共有媒体と参加を表せない。複数 Port を参照する segment profile を候補にするが、共通 consumer の媒体参照・独立寿命が必要なら新しいコア概念を検討する |
| Wi-Fi の AP と station | 一時点の AP–station 接続だけでは、共有無線媒体、所属、移動、通信品質を同じ事実として説明できない | 明示された二者の association を扱う profile と時刻の契約が必要。AP–station の線をケーブルや全 station 間の到達可能性に変換しない。association / roaming 全体は初期対応外 |
| trunk 上の VLAN と VRF | Node を Group に入れるだけでは、Port ごとの tagged/untagged、論理 interface、転送文脈を表せない | 論理 interface は Port 候補。VLAN の参加と tagging、VRF への関連付け、underlay は型付き関係が必要。profile の局所要素を他 profile / consumer が参照する要件は現 envelope では未解決 |
| シャーシと二つの line card | Group の親子では物理的な包含や Port の部材上の位置を区別できない | 端点を公開する module は Node として表せても、シャーシとの包含は別関係。部材 instance は物理 profile の候補。どの単位が Port を所有するかを adapter が明記し、自動で変えない |
| A から B への有向依存と A–B の配線 | 同じ Connection と矢印だけでは、依存方向と双方向の媒体を混同する | 依存 / flow は別の型付き関係とする。初期 Connection は方向を主張しない。依存 profile の図から配線の存在を推定しない |

これらにより、二端点コアは限定された用途で成立する候補だが、ネットワーク全般を単独で表す完成形ではないと判断する。
特に共有媒体、profile 間の参照、複数 topology の層間関係は「profile を置けば完成」と扱えない。
初期は未対応を診断し、必要性が出たときに比較表を更新する。

## 付帯する初期の選択

形や識別子の制約も、参照モデルからそのまま必須にしたものではない。

| 選択 | 比較した代案と初期の理由 | 境界 |
| --- | --- | --- |
| Node と Port を別 collection にする | Node 内への埋込も可能。端点・profile の参照と所有検査を直接行える形を初期候補にする | 論理的に正本が一つであれば、物理 DB の別 table までは要求しない |
| topology 内の全要素 ID を一意にする | kind ごとの一意でも型付き参照は成立する。初期は検査・参照索引・要素の追跡を単純にする | 世界共通の実機 ID ではない。他 topology の同じ文字列と統合しない |
| 属性を scalar と同型配列に限定する | 任意 JSON object も候補。初期は辞書の値型を小さくし、関係を不透明な属性へ埋めることを防ぐ | OTel の形が必須だからではない。用途別の構造化情報は profile で試し、表現不足なら型の追加を明示する |
| 名前や外部 key の一致で統合しない | 自動照合も候補だが、異なる用途・層の Node を同じ実機だからと一つにすると関係の意味が変わる | IdentityMap は実機の証拠だけでなく対応する要素の意味・文脈を確認する。複数 Node が同じ実体を参照する場合も保持できる必要がある |

## 拡張性を三段階で判定する

| 追加 | コア変更について言えること | 初期の確認 |
| --- | --- | --- |
| 既存要素への情報追加 | 既存 target を参照する長さ・部材情報などは profile 追加で試せる | P1 の route profile と未知 profile の保持 |
| 既存要素間の新しい関係 | profile 内の型付き関係は候補。ただし意味を使う consumer と参照制約が必要 | 紙上例で必要な契約を列挙する。汎用 renderer が自動で扱えるとはしない |
| 新しい独立要素・層間関係 | core の対象 kind、参照スコープ、適合 schema に追加が必要になる可能性がある | 初期未対応を明示する。profile 内の局所 ID を core ID と混同しない |

profile 一つの追加試験が証明するのは第一段階である。
第二・第三段階まで「コアを変えずにすべて追加できる」とは言わない。
schemaVersion があるだけでは古い consumer は新しい要素を扱えない。
公開前に対応する core 版・profile・用途と、未対応構造を拒否するか部分表示するかを宣言する。
構造の意味を変える変更は明示的な版の変更として扱う。

## 参照資料で確認したこと

参照規格は概念の比較に使う。以下から同じ wire format や runtime を採用する結論は導かない。

- RFC 8345 は network 間の supporting 関係を定義し、同じ実体を各 network の Node として表す場合も説明している。Node を実機そのものと同一視しない比較材料になる。[RFC 8345 §4.1](https://www.rfc-editor.org/rfc/rfc8345.txt)
- RFC 8343 は物理・論理 interface と interface layering を対象にする。Port を物理 connector だけに限定しない比較材料になる。[RFC 8343 §2・§3.3](https://www.rfc-editor.org/rfc/rfc8343.html)
- RFC 8348 は hardware component の包含関係を定義する。名前付き集合と物理的包含を区別する比較材料になる。[RFC 8348](https://www.rfc-editor.org/rfc/rfc8348.html)
- OTel Telemetry Schemas は規約の進化を限定した目的としており、すべてのデータ形状や想定し得る変換を扱わない。Shumoku でも初期範囲を明示する参考になる。[Telemetry Schemas](https://opentelemetry.io/docs/specs/otel/schemas/)
- containerlab の定義は実行環境の設定を含む。対応する静的構造を adapter で試すが、起動設定をコアの分類根拠にはしない。[Topology definition](https://containerlab.dev/manual/topo-def-file/)

## M0 の判定と P1 へ渡す作業

紙上レビューでは、ID と説明の分離、構造と View の分離、出所と未知値の扱いは残す。
Group 階層と混在した Connection.kind は外す。
二端点の限定、Group の必要性、端点参照の方式、拡張参照の方式は明示的な比較対象になった。
最小分離案との比較と表示範囲の変換も M0 の対象に追加する。
外部レビューや実装による適合確認が済んだことを意味しない。

まず P1a で最小分離案と再編案を比較し、構成・selection・presentation の境界を試す。
P1b では次の五件を確認する。各項目の証拠は [実装計画](network-model-implementation-plan.ja.md)に反映する。

1. Group なし・source 機能なしの静的 topology を独立 consumer が読める。名前付き集合を使う場合は表示以外の参照例も示す。
2. Connection の slot 案と端点 ID 案を、入替・付替え・保存後の profile 参照で比べる。
3. envelope 案と宣言的参照パス案を、小さな既知 profile と未知 profile の保持・影響列挙で比べる。
4. 部分的な観測と対応範囲外の関係を、情報の捏造や誤入力扱いをせず診断する。sequence は収集試作の方式として試す。
5. 最小編集・複数 View・静的 containerlab 変換・一つの profile を試し、初期範囲内の意味が同じことを確認する。

比較で方式が成立しなければ、公開前に論理設計と fixture を変更する。
未対応の共有媒体を二端点へ偽装する、包含を Group に入れる、独立 consumer が Editor 状態を要求する、
という結果は土台の成立とは認めない。
